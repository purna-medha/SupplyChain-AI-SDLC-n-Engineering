# Draft lab · B3 · Investigate, retain a draft and review its next action

Scope, timing and completion guidance are provisional until the teaching
content is finalized. These instructions accompany the existing starter.

**Use case:** an operations colleague asks you to investigate a container's
dwell status and fees, prepare a short update, and retain it for review.
An update can enter a local lab outbox only after the exact payload is approved.

Review the [B3 slides](../../slides-md/b3-agentic-workflows.md) and the
[B3 snippet sequence](../../snippets/b3/README.md). Work only in the TODO
functions at the top of `b3.py`. The tools and runner below them are supplied.
B3 has working read tools of its own; unfinished B2 code is not imported.

**Target: 30–40 minutes**, with dependencies/services ready. Choose two
exploration questions below. The specialist comparison is an optional follow-on;
the core remains one investigation and its reviewed local action.

## 1. Prescribe a simple route · about 3 minutes

Implement **B3.1 `choose_route(status)`**:

| Observed status | Route |
| --- | --- |
| OVERDUE | investigate |
| IN_TERMINAL or GATED_OUT | finish |
| unknown | clarify |
| Any unfamiliar label | review |

```bash
python b3.py route
python b3.py route --container C2
python b3.py route --container C9
```

This checkpoint is prescribed Python control flow. It makes no model call.
Explain why missing data must not be classified as an overdue container.
The next checkpoint is an alternative where an agent selects its next read;
the route function is not silently acting as its planner.

## 2. Delegate the investigation · about 8 minutes

Implement **B3.2 `make_investigator()`** using one SDK `Agent` and the supplied
`record_plan`, `read_status` and `read_fee` tools. These are already decorated
`function_tool` objects. Describe the required behavior in its instruction:

- Record a brief intended checklist, then obtain status before deciding what else is needed.
- For an overdue container, inspect its calculated fee before drafting.
- For a known non-overdue container, report its observed condition.
- For an unknown ID, request clarification instead of inventing a record.
- Return a short draft, preserve source/uncertainty, and never claim to send or approve it.

The provided tools print actual observations and retain them in `findings`.
The arithmetic belongs to the supplied data source, not the language model.
The runner bounds turns; it supplies no hidden successful draft.

## 3. Retain the actual result · about 5 minutes

Implement **B3.3 `save_task(state, path)`**. Write the supplied dictionary as
JSON. Its keys are `container_id`, `findings`, `draft` and `review`. The runner
supplies the real generated draft and initializes review to `pending`.

```bash
python b3.py investigate
python b3.py follow-up
python b3.py follow-up --new-session
```

**Observe:** inspect PLAN versus actual OBSERVATION output. Open the printed
task JSON and locate the source observations, actual draft and pending review.
The follow-up uses a reopened SQLite conversation; compare it with an empty
session. Task JSON and conversation history are distinct stores. Neither is
approval authority or a paused runtime checkpoint.

Try another known ID, an unknown ID, and a one-turn budget:

```bash
python b3.py investigate --container C2
python b3.py investigate --container C9
python b3.py investigate --max-turns 1
```

Check the actual tool choices and final text. A limit means incomplete;
it does not become a completed investigation. An earlier saved draft remains
an earlier draft if a later run fails. Rerun the default investigation with
the normal budget before continuing to review.

## 4. Review the exact action · about 12 minutes

Implement **B3.4 `make_review_agent()`** with only the supplied
`queue_customer_update` tool. Its decorator already sets `needs_approval=True`.
Instruct the agent to submit the supplied payload unchanged and to stop on
rejection. This agent is separate from the investigator; it consumes the
saved draft, rather than generating a replacement message.

Implement **B3.5 `review_pending(saved, decision)`**. Validate the terminal
input before changing state. Only `approve` and `reject` are accepted. For
each pending call, apply the corresponding SDK state method. Invalid input
must raise `ValueError`, leaving the action unexecuted.

```bash
python b3.py review
```

Read PENDING: tool name, identifier and complete text. The supplied runner
saves/restores actual `RunState` before asking for your decision. Approve
only after inspecting that payload. Check the task JSON and `work/outbox.jsonl`:
the outbox entry must preserve the exact reviewed draft. No customer message
is sent.

Prepare a new draft with `python b3.py investigate`, review it again, and type
`reject`. A rejection adds no entry. Previous approved entries remain, so
compare the outbox before/after instead of expecting the whole file to be
empty. Repeat with invalid input; no action should run. A fresh proposal
needs fresh review and is never automatically approved.

Completion means you can show a saved factual draft, a remembered follow-up,
an actual approval interruption and both review outcomes. Do not infer any
of those outcomes from generated prose alone.

## Explore the same lab · choose two

Allow about seven minutes. Use the [exploration method](../EXPLORATION.md). Compare actual observations,
stored state and effects; do not infer execution from the agent's final prose.

1. **Who actually chooses the next step?** Compare `python b3.py route` with
   `python b3.py investigate`. Locate where `choose_route` is called in the
   runner. Is that function choosing the investigator agent's tools, or are
   these two different arrangements? Which actual observations supported the
   agent's decision to investigate further?

2. **Does a proposed plan establish completed work?** Compare PLAN with
   OBSERVATION output from the same investigation. If the plan mentions a fee
   lookup, where is the evidence that it ran? Try `--max-turns 1`: which work
   occurred before stopping, and was a new completed draft saved? A previous
   task file may remain; identify whether it belongs to this new run.

3. **Does saving task data automatically give the model conversation history?**
   Compare `python b3.py follow-up` with
   `python b3.py follow-up --new-session`. The task JSON still exists in both
   cases. Inspect which store the runner passes to the model, and which holds
   findings/review status. A correct guess in a fresh session does not itself
   establish that the missing conversation was available.

4. **Which event establishes that an action happened?** Compare outbox contents
   before/after approval and before/after rejection. Can a generated sentence
   saying “queued” change the file? Which code actually writes it, and which
   decision permits that tool body to execute? Existing approved entries can
   remain, so compare effects for the current proposal.

5. **What does a completed review prevent here?** After completing a review,
   rerun `python b3.py review` without preparing a new investigation. Inspect
   the saved review field and the rejecting check. What does this establish
   about this task, and what would still need consideration for a changed draft
   or a different application's action? Do not infer general transactional
   guarantees from this small classroom outbox.

## Optional: compare ownership with specialists

The supplied `specialists()` factory creates distinct operations and charges
agents. Implement **B3.X1 `make_coordinator(operations, charges)`** by exposing
both through `.as_tool(..., max_turns=4)`. The coordinator owns the combined
reply. Implement **B3.X2 `make_triage(operations, charges)`** with `handoffs`
so the selected specialist owns the reply.

```bash
python b3.py specialists
python b3.py handoff
```

Compare actual read evidence and FINAL OWNER. Change `--question` to ask about
status instead of fees. Each nested run has its own turn bound; the outer
limit is not a global tool/token/cost budget. Explain whether this small
enquiry actually needs multiple agents before adding them to a real system.
