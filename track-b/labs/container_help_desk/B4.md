# B4 lab · Query permitted database records

**Start:** open [b4.py](b4.py), implement `inspect_schema`, then run `python b4.py schema`.

Build a database-backed fee capability, inspect its generated SQL and check whether its calculation answers the business question. Use the [B4 slides](../../slides-md/b4-enterprise-data.md) and [six complete examples](../../snippets/b4/README.md) as references.

Complete [lab setup](README.md#prepare-once), including the updated requirements. Run all commands below **from this lab folder with its environment active**. B1–B3 code is not imported. Every command creates fresh in-memory databases; no server or production data is needed.

**Plan 60 minutes:** about 45 for five checkpoints, 10 for two experiments and 5 to explain the evidence. This is a teaching estimate awaiting an instructor timing run.

## The business contract

| Container | Owner | Recorded status | Recorded USD fee |
| --- | --- | --- | --- |
| C1 | A | delayed | 100 |
| C2 | B | delayed | 200 |
| C4 | A | delayed | 50 |
| C5 | A | on_time | 75 |

Caller A's delayed total is **150 USD**. C5 is excluded by status; C2 is excluded by ownership. Snapshot time is `2026-11-06T00:00:00Z`. A recorded fee is not automatically an outstanding balance.

[b4_data.py](b4_data.py) supplies the source and projects A's permitted fee/event rows into a separate database. It removes owner/private-note fields from the fee projection. A separate synthetic private table supports the denial probe. The model sees only the approved fee-table schema and permitted query results. The caller is a host-owned fixture, not real authentication.

## 1 · Inspect what a row represents · 5 minutes

**Understand:** the source has one fee row per container, while `events` can contain several rows per container. Keys describe relationships; they do not define a fee's business meaning.

Implement **B4.1 `inspect_schema(engine)`** using SQLAlchemy Inspector. Return this shape for each table:

```text
{table_name: {"columns": [names], "primary_key": [names], "foreign_keys": [metadata]}}
```

Use `get_table_names`, `get_columns`, `get_pk_constraint` and `get_foreign_keys`. Extract column names and the primary key's `constrained_columns`; retain the supplied foreign-key dictionaries.

**Predict:** which table can have multiple rows with the same container ID?

```bash
python b4.py schema
```

**Inspect:** locate `container_fees.container_id` as a primary key and `events.container_id` as a declared foreign key. Explain why joining events could repeat an amount. This checkpoint is offline.

## 2 · Implement a scoped fixed read · 10 minutes

Implement **B4.2 `read_fee(engine, container_id, trusted_owner)`**:

- Use a fixed SQL statement through `text()` and separately bind `:id` and `:owner`.
- Require both the requested ID and the trusted owner to match; cap the result at one row.
- Select only `container_id`, `fee`, `currency` and `as_of`.
- Return `dict(row)` from `.mappings().first()`, or `None` when absent.

The runner supplies caller A and validates your returned fields with Pydantic. This shape check cannot supply missing ownership enforcement.

**Predict:** C2 exists. Should caller A receive its fee?

```bash
python b4.py read
python b4.py read --container C2
python b4.py read --container C9
```

**Inspect:** C1 supplies 100 USD and observation time. C2 and C9 both print `unavailable`, without a fee. Private notes/owner must not appear. These commands are offline.

## 3 · Repair the calculation's grain · 8 minutes

New question: **total recorded USD fees for delayed containers with at least one event**.

The supplied wrong join repeats C1's fee for its two events. Implement **B4.4 `event_fee_total(engine)`** with a fixed `SUM` query whose `EXISTS` condition checks event membership without repeating each fee. Filter delayed status and USD. Execute it and return the scalar result.

**Predict:** what does the wrong join sum, and what should your query sum?

```bash
python b4.py grain
python b4.py grain --equal-fees
```

**Inspect:** default wrong total 250 versus intended 150. With C4's fee changed to 100, wrong total 300 versus intended 200. `SUM(DISTINCT fee)` is not a repair: it collapses equal amounts from different containers. Keep the independently established expectation visible. Both commands are offline.

## 4 · Add question-to-SQL with enforced execution limits · 11 minutes

First inspect the supplied database boundary; no model is needed:

```bash
python b4.py boundaries
```

**Inspect:** two visible approved rows, `TRUNCATED: True`, and rejection of a private-table read and DELETE. The SQLite authorizer enforces table/operation restrictions. Its separate progress callback interrupts excessive query instructions. A display cap does not bound earlier database work.

Implement **B4.3 `make_query_engine(database)`**. Construct `llama_index.llms.openai.OpenAI` with `gpt-4.1-mini`, temperature 0 and `os.environ["OPEN_AI_KEY"]`. Return `NLSQLTableQueryEngine` with:

```text
sql_database=database, tables=["container_fees"], llm=your_llm,
synthesize_response=False, context_str_prefix=CONTEXT
```

The supplied runner caches schema before installing the SQLite policy and disables unused embedding setup. `include_tables` supplies schema context; it is not database authorisation.

**Predict:** independently derive the delayed total before running:

```bash
python b4.py query
```

**Inspect:** the actual generated SQL, `ROWS: [[150]]`, independent `[[150]]` and `CHECK: PASS`. SQL can vary. A rejected/failed query stops rather than becoming an empty result or zero. **This command makes a model call.**

## 5 · Give the familiar agent the capability · 11 minutes

Implement **B4.5 `make_agent(query_tool)`** with an SDK `Agent`, `gpt-4.1-mini` and only the supplied query tool. Instruct it to use actual database evidence, preserve currency and exact source/time, report empty/failed/truncated results honestly and not retry a failed query.

```bash
python b4.py agent
```

**Inspect:** `TOOL QUESTION`, actual `SQL` and `ROWS`, then `ANSWER`. Check 150 USD, source `approved-fee-snapshot/A` and the exact snapshot timestamp. Both the outer agent and inner SQL generation make model calls. Generated explanations still need inspection.

Completion evidence: schema/relationship output, permitted and unavailable fixed reads, repaired totals on both fixtures, actual SQL/rows, rejected operations and the final agent explanation.

## Explore the same lab · choose two

Use [predict → change → run → inspect → explain](../EXPLORATION.md).

1. **Does input text become SQL?** Run `python b4.py read --container "C1' OR 1=1 --"`. Expect one unmatched bound value, not all records. Identify where binding and ownership are enforced separately.
2. **Does the generated calculation follow the changed question?** Run `python b4.py query --question "What is the maximum recorded USD fee for delayed containers?" --expected-json "[[100]]"`. Inspect the changed SQL and independently expected result.
3. **Does no matching record mean zero?** Run `python b4.py query --question "What is the recorded USD fee for container C2?" --expected-json "[]"`. Inspect actual empty rows. Try the same question through `agent`; compare its wording with the observation.
4. **Does a larger display cap change permission?** Run `python b4.py boundaries --row-cap 3`. All three public rows should be visible without truncation; forbidden operations should remain rejected.
5. **Does a stop mean nothing ran?** Run `python b4.py agent --max-turns 1`. Inspect which tool/query operations occurred before the explicit incomplete outcome. No final answer is promised.

## Boundaries to explain

This lab demonstrates a trusted projection and a restricted toy SQLite connection. It does not implement an identity provider or portable production isolation. Changing the database URL does not transfer SQLite callbacks. The instruction callback is not a wall-clock or cumulative workflow deadline. The query result is fetched before the five-row outer-model cap, so that cap alone does not bound memory/work. Schema inspection and the grain checkpoint use supplied unrestricted local engines; only query/agent execution receives the restricted analytics path.

Keep writes/retries optional through the [B4 integration references](../../snippets/b4/reference/integrations/README.md). No write workflow is required to finish this lab.
