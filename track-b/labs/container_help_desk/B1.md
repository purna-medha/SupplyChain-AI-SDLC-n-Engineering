# Draft lab · B1 · Help a new colleague understand shipping terms

Scope, timing and completion guidance are provisional until the teaching
content is finalized. These instructions accompany the existing starter.

**Use case:** a new operations colleague asks what dwell time means, then asks
how it differs from detention. Build a useful conversation and inspect what
each request consumes. This module reads no container records.

**Before coding:** review the [B1 slides](../../slides-md/b1-llm-applications.md)
and the [model/instruction/history snippets](../../snippets/b1/README.md).
Complete the [lab setup](README.md) first. Edit only the TODO bodies in `b1.py`.

**Target: 30–40 minutes**, including exploration, with model access prepared.
Use the [exploration method](../EXPLORATION.md) and choose two questions below.
The remaining questions and hosted/local comparison are optional follow-ons.

## 1. Connect the model · about 8 minutes

Implement **B1.1 `ask_model(messages, model)`**. The imports, question, model
name and runner are supplied. Use the same LiteLLM call as the first snippet.
Return the full response, so the runner can read its text and usage metadata.
Use the provided output limit and temperature. Credentials come from the
environment. Start with the hosted model.

```bash
python b1.py call
python b1.py call --question "What is demurrage in shipping?"
```

**Observe:** an actual reply, elapsed seconds, input/output tokens and estimated
USD cost. Compare the explanation with the shipping meaning. A successful
request does not prove the explanation is correct. Service and access errors
are real failures to diagnose; there is no fallback prepared answer.

## 2. Give the application a consistent role · about 5 minutes

Implement **B1.2 `make_messages(question, instruction)`**. Return the supplied
behavioral instruction as a system message, followed by the user's question.
The instruction describes a colleague-facing explanation; it supplies no
operational facts.

```bash
python b1.py instruction
python b1.py instruction --question "What is C1's current recorded status?"
```

**Observe:** compare the presentation with checkpoint 1. For the second
question, inspect whether the model acknowledges its missing record access.
An instruction requests that behavior; check the actual reply.

## 3. Make a follow-up understandable · about 10 minutes

Implement **B1.3 `add_follow_up(messages, reply, question)`**. Keep the earlier
request, append the actual assistant reply, then append the new user message.
Return the resulting history. Do not substitute a prepared assistant response.

```bash
python b1.py history
python b1.py call --question "How does that differ from detention?"
```

**Observe:** the history checkpoint prints the second request. Identify which
message establishes what “that” refers to. Compare the second call's input
usage with the isolated follow-up. The exact wording and token counts vary.

## Explore the same lab · choose two

Predict before each change, inspect the actual result and restore the baseline
before the next experiment. Record a short explanation using the shared method.

1. **Does an instruction add facts or change requested behavior?** Keep the
   question/model fixed and change `INSTRUCTION` from two sentences to three
   numbered points. Run `python b1.py instruction`. Inspect presentation,
   correctness and usage separately. Did a different writing style give the
   application any access to current container records?

2. **Where does a follow-up's context come from?** Temporarily change
   `add_follow_up` so the second request retains its system instruction and
   newest question but omits the first user/assistant exchange. Run
   `python b1.py history` and inspect SECOND REQUEST to confirm the change.
   If the model still gives a plausible answer, what could it infer without
   that exchange? Does plausibility establish conversational memory?

3. **Can context remain after removing the earlier user question?** Retain
   the actual first assistant reply while omitting only the first user message
   from the second request. Inspect whether the retained reply names the topic.
   Which message now supplies the evidence for what “that” refers to?

4. **Is nonempty output enough to call the task complete?** Temporarily make
   the output limit very small and request a longer explanation. Inspect the
   actual text and `response.choices[0].finish_reason` inside `ask_model`.
   What would the application need to check beyond receiving some text?

5. **What can two repeated calls establish?** Repeat the same request with
   temperature and other settings unchanged. Compare actual wording, token
   usage, time and cost. If the wording matches, does that establish that every
   future request is deterministic? If it differs, which measurement changed?
