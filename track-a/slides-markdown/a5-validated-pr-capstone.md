# A5-01 · Delivery from brief to a validated PR

A5 combines the working methods from A1–A4 on a fresh, bounded change.

The outcome is a reviewable PR with understood code, requirement-linked checks, a justified readiness decision and a handover another developer can use.

Most of this module belongs to participant work and peer review.

---

# A5-02 · A5 agenda

1. Frame the change and select a workflow
2. Specify, plan and implement through tests
3. Verify with the harness and review
4. Demonstrate readiness and hand over
5. Transfer the practice into team work

Use the methods that help the task, with evidence for the decisions made.

---

# A5-03 · A fresh brief should require a new decision

The final lab uses a fresh capstone change with a validation, interface or compatibility difference from the instructor's examples.

Identify intended behaviour, non-goals, acceptance cases and unresolved choices before editing.

> **Capstone slot A5-E01:** the client-specific brief, independent starting checkpoint and relevant project context, without a step-by-step solution.

---

# A5-04 · Illustrative brief: unavailable ETA

**Written illustration:** the classroom shipment source may now provide no ETA value. Preserve the established numeric and cancellation behaviour.

Identify the absent-value representation, result/error policy and its interaction with cancellation before proposing implementation.

This shows the kind of changed requirement suitable for independent practice. It does not prescribe the client capstone domain or replace its task brief.

---

# A5-05 · Tool choices should have a task-specific reason

Choose model tier and context according to the uncertainty and scope of the change.

Use a connected source when a relevant fact is missing. Apply a skill when its method fits. Delegate only a bounded task whose output can be reviewed.

Explain both the choice and the evidence needed to judge it.

---

# A5-06 · The preparation package makes intent inspectable

Verify the affected source and caller. Resolve consequential requirements and compare plausible approaches.

Record a sufficient specification and reviewed plan, including what must remain unchanged and how completion will be checked.

Give the assistant a bounded assignment that cites those artifacts and states stopping conditions.

---

# A5-07 · Implementation needs a retained expectation

Lead one suitable behavioural increment through an intended failing test and a passing implementation.

Inspect the diff and preserve legitimate expectations. If work deviates, determine whether requirements, context, the plan or code need correction.

> **Capstone slot A5-E02:** participant-owned test-first evidence and one explained implementation decision.

---

# A5-08 · The final harness run belongs to the final revision

Run the relevant checks and inspect actual outcomes. State missing checks or limitations accurately.

Review source, tests and configuration together, including any change made to obtain a pass.

Do not reuse an earlier success as evidence for a later diff without establishing that the relevant checks still apply.

---

# A5-09 · Peer review should challenge a consequential claim

Use an AI first-pass review and a peer's judgment to examine the specification, diff and checks.

Validate findings, address justified corrections and repeat affected checks. Explain one assumption the peer challenged and how evidence resolved it.

Unsupported criticism and unverified author claims both need examination.

---

# A5-10 · The demonstration connects intent to observed behaviour

Show the requested result and one meaningful boundary case. Explain the relevant code and the check supporting it.

Present the final diff, review response, remaining risks and merge-or-hold recommendation.

> **Capstone slot A5-E03:** final participant demonstration evidence for the supplied capstone lab variation.

---

# A5-11 · A handover should support the next bounded action

Identify the current checkpoint, accepted decisions, actual checks, remaining work and next action.

Explain a known-good recovery point and where code rollback would be insufficient if data or external effects existed.

Have the peer assess whether another developer could continue from the handover without reconstructing the chat.

---

# A5-12 · Adoption needs a baseline and a review decision

Select a recurring development task and name an owner, baseline, success measures and review date.

Include preparation, model/tool usage, implementation, review and correction effort alongside quality or rework.

Decide what outcome would justify keeping, revising or stopping the practice.

---

# A5-13 · A short teachback makes understanding visible

Explain one consequential decision from the change:

- The requirement or uncertainty
- The method selected
- The evidence observed
- The limitation that remains

Identify what transfers to another repository and what depends on local rules or tooling.

---

# A5-14 · Capstone evidence checklist

| Capability | Evidence to present |
| --- | --- |
| Preparation | Source-backed specification and plan |
| Implementation control | Bounded request, understood diff and correction |
| Verification | Meaningful failing/passing case and current checks |
| Review judgment | Validated finding or justified rejection |
| Continuity | Readiness statement and usable handover |

The resulting behaviour and the working method both matter.

---

# A5-15 · What acceptable reasoning looks like

For the final capstone change, a satisfactory response:

- Identifies owner decisions and relevant source facts
- Covers a consequential combination or boundary case
- Preserves required existing behaviour and interfaces
- Links checks to requirements
- Reports actual results and unexecuted work accurately

Judge the developer's working method alongside the resulting software.

---

# A5-16 · Capstone review discussion

**Scenario:** the change behaves correctly in the demonstration, but the new tests omit a stated compatibility case and the handover says “all requirements verified.”

What should the participant correct before recommending acceptance?

Distinguish a missing check from a confirmed implementation defect.

---

# A5-17 · Track A completion

You can now prepare a change, direct an assistant, verify its results, use a quality harness and explain a reviewable delivery decision.

Carry the same discipline into work: explicit intent, relevant context, bounded execution and inspected evidence.

Track B develops a different capability: building models, tools and agents into application runtime behaviour.
